# 六、优化机制在各模型间的适用性

## 概览

| 优化机制 | DeepSeek | OpenAI | Anthropic Claude | Google Gemini | 本地 Ollama |
|----------|----------|--------|------------------|---------------|-------------|
| 自动前缀缓存 | ✅ **自动** | ✅ prompt_caching（需设置 `ephemeral`） | ✅（需 `cache_control` 参数） | ❌ 无 cache | ✅（KV cache 本地自动） |
| 上下文压缩 | ✅ 通用 | ✅ 通用 | ✅ 通用 | ✅ 通用 | ✅ 通用 |
| 消息只追加不修改 | ✅ 必要 | ✅ 必要 | ✅ 必要 | ✅ 必要 | ✅ 必要 |

## 详细分析

### DeepSeek — 自动前缀缓存（零配置）

**缓存方式：** 服务端自动缓存消息数组前缀，无需任何请求参数。

**要求：**
- 请求前缀的字节级一致性
- 每次请求的 `messages[0]`（system role）必须完全相同
- 每次请求的 `tools` 数组必须完全相同
- 价格：缓存命中 ¥0.02/1M tokens vs 普通 ¥1/1M tokens（便宜 50×）

**适用场景：** 多轮对话、agent 循环。不适用一次性请求。

### OpenAI — Prompt Caching（需显式标记）

**缓存方式：** 需要在请求中设置 `cache_control` 参数标记哪些消息可缓存。参考：[OpenAI Prompt Caching](https://platform.openai.com/docs/guides/prompt-caching)

**要求：**
```json
{
  "messages": [
    {"role": "system", "content": "...", "cache_control": {"type": "ephemeral"}},
    ...
  ]
}
```
- 需要至少 1025 个 token 的连续前缀才能触发缓存
- 缓存价格：普通输入的 50% off（vs DeepSeek 的 98% off）
- 命中率取决于前缀长度

**适配方法：** 在消息结构的 system message 和最早的几条消息上添加 `cache_control` 标记。

### Anthropic Claude — Prompt Caching（需显式标记）

**缓存方式：** 需要在请求中设置 `cache_control` 标记。参考：[Anthropic Prompt Caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)

**要求：**
```json
{
  "messages": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."},
    {"role": "user", "content": "..."}
  ],
  "system": [{"type": "text", "text": "...", "cache_control": {"type": "ephemeral"}}]
}
```
- 需要至少 1024 个 token 的连续前缀
- 缓存价格：读取 1/10 的价格（90% off）
- 需要显式在 system 或 messages 中标记可缓存的位置

**适配方法：** 在 system prompt 和最早的 user/assistant 消息对上添加 `cache_control: {type: "ephemeral"}`。

### Google Gemini — 无缓存机制

Gemini API 当前不提供 prompt 级缓存。所有 prompt token 每次都重新计费。

### 本地 Ollama — KV Cache（本地自动）

Ollama 在本地运行时会维护 KV cache。如果连续请求的前缀相同，本地 GPU 的 KV cache 自动命中，加快推理速度。但这不是 API 级的计费节约——因为是本地运行，token 成本为零。

## 核心机制跨模型对比

### 必须做的（所有模型都适用）

| 策略 | 原因 |
|------|------|
| System message 只构建一次 | 所有缓存的先决条件 |
| 消息只追加不修改 | 所有缓存的先决条件 |
| 工具列表稳定 | 工具 schema 也是 prefix 的一部分 |
| 上下文压缩 | 控制上下文窗口大小，避免超出限制 |
| 工具输出截断 | 降低每次请求的 token 消耗 |
| Token Economy 模式 | 减少固定 prefix 大小 |

### DeepSeek 独有的

| 策略 | 原因 |
|------|------|
| **无特殊参数** | 缓存自动生效，不需要额外配置 |
| **reasoning_content 回传** | tool call 轮必须回传，否则 400 error |
| **content 字段不能省略** | DeepSeek 的严格 deserializer 拒绝缺少 content 的消息 |

### OpenAI/Anthropic 需要的额外工作

| 策略 | 原因 |
|------|------|
| 添加 `cache_control` 标记 | 需要显式告诉 API 哪些部分可缓存 |
| 至少 1024+ token 的前缀 | 缓存触发的最低长度要求 |

## 总结

**Reasonix 的大部分 token 节约优化都是通用的**，不依赖 DeepSeek 特有功能。核心模式——保持 prefix 稳定、只追加不修改、需要时压缩——同样适用于 OpenAI 和 Anthropic。

唯一的 DeepSeek 专属优化是 `reasoning_content` 回传（用于 thinking mode）和自动缓存（不需要额外参数）。

若要将这套模式迁移到其他模型：
1. **对于 OpenAI/Anthropic**：在 system message 和历史消息上添加 `cache_control` 标记
2. **对于 Gemini**：无法利用前缀缓存，但仍可使用压缩和截断策略减少 token
3. **对于本地 Ollama**：策略带来的 KV cache 命中可加速推理
