## 一、分支策略

### 1.1 总体原则

1. **`upstream/main-v2` 是上游官方分支**，只读同步，不直接修改
2. **`wkj-cli` 是本地集成二开基线**，接收已经验证过的功能和上游同步
3. **`release/wkj-cli-stable` 是本地最稳定发布基线**，只从 `wkj-cli` 接收验证稳定的快照
4. **所有新功能从 `wkj-cli` 切出独立 `feature/` 分支**，验证后再合并回 `wkj-cli`
5. **临时工作分支用完即删**，不在个人工作分支上长期开发
6. **`wkj-cli`、`feature/*`、`release/*` 不上 GitHub**，未来通过局域网 git 仓库共享

### 1.2 为什么需要 release/wkj-cli-stable

- `wkj-cli` 会定期同步 `upstream/main-v2`，同步过程中可能出现冲突或回归
- `release/wkj-cli-stable` 作为“只读消费”基线，不直接合并上游，避免被上游更新破坏
- 当 `wkj-cli` 验证稳定后，再同步到 `release/wkj-cli-stable`
- 如果日常使用时发现 `wkj-cli` 有问题，可以立刻回退到 `release/wkj-cli-stable`

### 1.3 为什么不上 GitHub

- 这些分支包含基于个人使用习惯的定制功能（如 `sendtab`），不具备通用性
- 避免上游仓库被个人二开分支污染
- 局域网内部共享已足够满足团队需求

## 二、分支命名约定

| 前缀 | 含义 | 生命周期 | 基线 | 示例 |
|------|------|:-------:|:----:|------|
| `release/` | 本地稳定发布分支 | 长期 | `wkj-cli` | `release/wkj-cli-stable` |
| `feature/` | 本地二开功能分支 | 中短期 | `wkj-cli` | `feature/sendtab` |
| `fix/` | 本地修复分支 | 短期 | `wkj-cli` | `fix/desktop-crash` |
| `sync/` | 上游同步临时分支 | 一次性 | `wkj-cli` | `sync/20260615` |
| `release-` | 上游版本的发布验证分支 | 短期 | `upstream/main-v2` | `release-1.7.0-ALOOP-V1` |
| `tmp-dev-YYYYMMDD-` | 个人临时探索/调试分支 | 一次性 | 任意 | `tmp-dev-20260615-sendtab` |

### 2.1 临时工作分支

- 用于快速验证、探索、联调
- **命名规范**：`tmp-dev-YYYYMMDD-<简短描述>`
  - 例如：`tmp-dev-20260615-sendtab`、`tmp-dev-20260616-ui-test`
- 从 `wkj-cli` 或 `feature/*` 切出，按需选择基线
- **不推送到任何 remote**
- 功能拆分完成后应立即删除

### 2.2 历史遗留的临时分支

此前使用的 `kimi27-claude-001` 等命名方式已废弃，未来统一使用 `tmp-dev-YYYYMMDD-` 前缀。文档中的旧示例仅作历史参考。

## 四、标准工作流

### 4.1 新增功能

```bash
# 1. 更新基线
git checkout wkj-cli
git merge upstream/main-v2  # 或先处理上游同步

# 2. 创建功能分支
git checkout -b feature/xxx

# 3. 开发并验证
# ...
go test ./...
cd desktop/frontend && npx tsc --noEmit

# 4. 合并回基线
git checkout wkj-cli
git merge --no-ff feature/xxx -m "merge: xxx 功能"

# 5. 可选：打标签
git tag wkj-cli-vx.x-xxx
```

### 4.2 同步上游

详见 [上游合并最佳实践与自动化机制.md](上游合并最佳实践与自动化机制.md)。

简要流程：

```bash
git checkout wkj-cli
git fetch upstream
git merge upstream/main-v2
# 解决冲突
# 编译、测试、手动验证
```

### 4.3 更新 release 分支

`wkj-cli` 验证稳定后，再同步到 `release/wkj-cli-stable`：

```bash
# 1. 确认 wkj-cli 当前状态稳定
# 2. 同步到 release 分支
git checkout release/wkj-cli-stable
git merge wkj-cli --no-ff -m "release: sync stable from wkj-cli"

# 3. 打标签
git tag v1.x.x-wkj
```

**原则**：

- `release/wkj-cli-stable` 不直接合并 `upstream/main-v2`
- 只有 `wkj-cli` 经过充分验证后，才同步到 release
- 如果 `wkj-cli` 上游同步后出现问题，release 分支不受影响

### 4.4 清理临时分支

```bash
# 确认分支已合并
git branch --merged wkj-cli

# 删除已合并的本地临时分支
git branch -d kimi27-claude-001
```

## 五、分支备注与个人说明

### 5.1 `wkj-cli`

- **定位**：团队内部集成二开基线
- **来源**：从 `upstream/main-v2`  fork 并持续同步
- **包含内容**：
  - 上游 `main-v2` 的代码
  - 已验证的本地功能（如 `sendtab`）
  - 本地维护文档（`my-docs/`）
- **使用方式**：日常开发基于此分支，新功能从它切出，上游同步直接在此分支处理
- **稳定性**：集成中，可能因上游同步出现临时问题
- **推送范围**：仅局域网 git 仓库

### 5.2 `release/wkj-cli-stable`

- **定位**：**最稳定的本地发布基线**
- **来源**：从 `wkj-cli` 切出
- **用途**：
  - 保存 `wkj-cli` 验证稳定后的快照
  - 作为日常使用的“保底”版本
  - 当 `wkj-cli` 被上游更新破坏时，可快速回退
- **更新方式**：
  - 不直接合并 `upstream/main-v2`
  - 只通过 `git merge wkj-cli` 接收稳定状态
- **使用场景**：
  - 正式演示、重要任务前切换到该分支
  - `wkj-cli` 上游同步后不稳定时，回退到该分支
- **推送范围**：仅局域网 git 仓库

### 5.3 `feature/sendtab`

- **定位**：sendtab 跨 Tab 消息功能的独立分支
- **来源**：从 `wkj-cli` 切出
- **用途**：
  - 向另一个已打开的 Desktop Tab 发送消息
  - 目标 Tab 会显示 `MessageFromTab[<源Tab标题>]: <消息>`
  - 时间线标记为蓝色
- **风险说明**：
  - 跨 Tab 发送消息会污染目标 Tab 的上下文
  - 可能被 agent 误用，导致消息发到错误 Tab
  - 属于个人使用习惯功能，不通用
- **使用建议**：
  - 仅在明确知道目标 Tab 用途时使用
  - 不要发送敏感、重要或不可逆的指令
  - 目标 Tab 未明确响应时，不要连续发送
- **推送范围**：仅局域网 git 仓库

### 5.4 `release-1.7.0-ALOOP-V1`

- **定位**：A-Loop 功能发布验证分支
- **来源**：从 `upstream/main-v2` 切出
- **用途**：验证 A-Loop 功能在 v1.7.0 基线上的稳定性
- **状态**：临时分支，验证完成后合并或废弃

## 七、常见问题

### Q1：为什么功能分支不直接基于 `upstream/main-v2`？

因为本地功能通常依赖 `wkj-cli` 上已有的其他二开改动或配置。基于 `wkj-cli` 可以减少重复解决冲突的工作。

### Q2：`feature/sendtab` 会合并回 `upstream/main-v2` 吗？

不会。`sendtab` 是基于个人使用习惯的功能，不通用，且存在跨 Tab 风险，不适合进入上游官方仓库。

### Q3：临时工作分支（如 `kimi27-claude-001`）什么时候删除？

当其中的有效改动已经拆分、合并到对应的功能分支或 `wkj-cli` 后，就可以删除。

### Q4：如何查看某个分支包含哪些改动？

```bash
# 查看分支相比基线的 commit
git log --oneline wkj-cli..feature/sendtab

# 查看分支相比基线的文件变化
git diff --stat wkj-cli feature/sendtab
```

### Q5：`wkj-cli` 上的文档改动需要走 feature 分支吗？

小文档改动（如修正笔误）可以直接在 `wkj-cli` 上修改。新增或重构整篇文档（如本次的上游合并最佳实践文档）建议先切一个 `docs/xxx` 或 `feature/docs-xxx` 分支，验证后再合并。
