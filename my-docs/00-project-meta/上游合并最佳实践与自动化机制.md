# 上游合并最佳实践与自动化机制

<!--
版本: v1.0
创建: 2026-06-15 00:00:00
更新: 2026-06-15 00:00:00
-->

> 适用场景：长期维护一个基于 `upstream/main-v2` 的二次开发分支（如 `wkj-cli`），需要持续同步上游更新。
>
> 核心矛盾：上游演进越快，本地二开改动越多，合并冲突的“识别成本”和“回归风险”就越高。

---

## 一、分支策略

### 1.1 推荐模型：Long-lived Fork + Short-lived Feature Branches

```
upstream/main-v2  ──────────────────────────────────────►
       │                              │
       │ 定期同步                     │ 独立 PR
       ▼                              ▼
  origin/main-v2 (fork) ──►  feat/xxx ──►  fix/yyy
       │
       │ 二开基线
       ▼
   wkj-cli (本地二开分支，永不 PR)
```

| 分支 | 用途 | 生命周期 | 是否提 PR |
|------|------|:-------:|:---------:|
| `upstream/main-v2` | 上游主分支 | 长期 | — |
| `origin/main-v2` | 本地 fork 的同步镜像 | 长期 | 否 |
| `feat/<name>` / `fix/<name>` | 向上游回馈的功能或修复 | 短期 | 是 |
| `wkj-cli` | 本地二开合集分支 | 长期 | 否 |

### 1.2 关键原则

1. **一个 PR 一个关注点**
   - PR 分支只包含能回馈上游的代码
   - 不包含 `my-docs/`、个人配置、实验性功能
2. **二开分支永远从 `origin/main-v2` 切出**
   - 不要在 `wkj-cli` 上直接开发新功能
   - 新功能先在 `feat/xxx` 上完成，再合并进 `wkj-cli`
3. **高频小额同步优于低频大额同步**
   - 每周至少同步一次上游
   - 单次合并冲突超过 20 个文件，说明同步间隔过长
4. **`my-docs/` 与代码分离**
   - 文档改动不进入 PR
   - 文档可以独立提交，不影响上游合并

## 二、冲突分类与处理优先级

### 2.1 冲突类型矩阵

| 类型 | 识别难度 | 处理复杂度 | 自动化可能性 | 示例 |
|------|:-------:|:---------:|:-----------:|------|
| **纯文本冲突** | 低 | 低 | ✅ 高 | 同一行被双方修改 |
| **导入/依赖冲突** | 低 | 中 | ⚠️ 中 | 上游新增 import，本地也新增 import |
| **配置 schema 冲突** | 中 | 中 | ⚠️ 中 | `reasonix.toml` 新增字段，默认值变化 |
| **接口契约冲突** | 中 | 高 | ❌ 低 | `Controller` 新增/删除方法 |
| **行为语义冲突** | 高 | 高 | ❌ 极低 | 同名函数逻辑改变，调用方需适配 |
| **前端状态冲突** | 高 | 高 | ❌ 低 | React reducer 结构变化，本地 UI 依赖旧字段 |

### 2.2 处理顺序建议

```
1. 先解决纯文本冲突（git 已标记）
2. 再处理导入/依赖冲突（编译器会报错）
3. 再处理接口契约冲突（go vet / tsc 会报错）
4. 最后处理行为语义冲突（需要人工 review + 测试）
```

## 三、标准同步流程

### 3.1 合并前预检

```bash
# 1. 保存当前工作区
git status                          # 确认无未提交改动
# 若有，先 stash 或提交到临时分支

# 2. 获取上游最新状态
git fetch upstream

# 3. 查看变更范围
git log --oneline --graph HEAD..upstream/main-v2

# 4. 统计影响文件
git diff --stat HEAD upstream/main-v2

# 5. 识别本地二开文件与上游重叠区域
git merge-tree $(git merge-base HEAD upstream/main-v2) HEAD upstream/main-v2 \
  | grep -E '<<<<<<|======|>>>>>>' || echo "无文本冲突"
```

### 3.2 合并执行

```bash
# 方式 A：直接在二开分支上合并（推荐，简单直接）
git checkout wkj-cli
git merge upstream/main-v2

# 方式 B：先创建隔离分支，验证后再合入（推荐，风险可控）
git checkout -b sync/upstream-$(date +%Y%m%d) wkj-cli
git merge upstream/main-v2
# 验证通过后：
git checkout wkj-cli
git merge sync/upstream-$(date +%Y%m%d)
```

### 3.3 合并后验证清单

| 检查项 | 命令/方法 | 通过标准 |
|------|---------|---------|
| 无未解决冲突 | `grep -R "<<<<<<< HEAD" --include="*.go" --include="*.ts" --include="*.tsx" .` | 无输出 |
| Go 编译通过 | `go build ./...` | 退出码 0 |
| Go 静态检查 | `go vet ./...` | 无新增错误 |
| 关键包测试 | `go test ./internal/control/... ./internal/agent/... ./internal/boot/...` | 退出码 0 |
| 前端类型检查 | `cd desktop/frontend && npx tsc --noEmit` | 无类型错误 |
| 桌面端可构建 | `cd desktop && wails build`（或 `go build ./desktop/`） | 退出码 0 |
| 自定义功能回归 | 手动启动 Desktop / TUI，执行关键路径 | 行为符合预期 |

## 四、冲突处理最佳实践

### 4.1 不要信任“自动解决”

- `git merge` 的递归策略可以自动合并很多变更
- 但如果涉及同一函数、同一配置段、同一路由，即使无 `<<<<<<<` 标记，也可能产生**静默语义冲突**
- 每次合并后，必须对“本地二开曾修改过的文件”做 diff review

### 4.2 维护“本地改动清单”

在二开分支根目录维护 `my-docs/00-project-meta/本地改动清单.md`：

```markdown
# 本地改动清单

| 文件 | 改动原因 | 上游冲突风险 | 上次 review 日期 |
|------|---------|------------|----------------|
| `internal/control/controller.go` | 新增 AddTool/AddCommand/AddSlashHandler | 高 | 2026-06-14 |
| `desktop/tabs.go` | 注册 sendtab 工具/命令/斜杠处理器 | 中 | 2026-06-14 |
| `desktop/frontend/src/components/Transcript.tsx` | MessageFromTab 蓝色时间线标记 | 中 | 2026-06-14 |
```

合并前先读这份清单，重点检查这些文件。

### 4.3 分阶段提交

合并解决过程中，建议分多次提交：

```bash
git add internal/control/controller.go
git commit -m "merge: resolve controller.go extension points"

git add desktop/
git commit -m "merge: resolve desktop sendtab registration"

git add desktop/frontend/src/components/Transcript.tsx
git commit -m "merge: resolve Transcript timeline markers"
```

优点：
- 回滚粒度细
- 便于 code review
- 冲突责任清晰

### 4.4 遇到无法判断的语义冲突时

1. **停止自动合并**，保留当前状态
2. 在临时分支上，用 `git show upstream/main-v2:<file>` 查看上游版本
3. 用 `git show HEAD:<file>` 查看本地版本
4. 用 `git difftool` 或 IDE 三栏对比
5. 必要时在上游仓库搜索相关 PR/commit message，理解变更意图
6. 决策：保留本地 / 采用上游 / 重新实现融合方案
7. 将决策理由写入提交信息或 `my-docs/03-feature-action/` 下的合并记录

## 五、Agent 自动化机制设计

### 5.1 能自动化的部分（可靠）

| 环节 | 自动化内容 | 触发方式 |
|------|-----------|---------|
| 上游状态监控 | 检测 `upstream/main-v2` 是否有新 commit | cron / GitHub Action |
| 预检脚本 | fetch、统计变更文件、检测文本冲突 | `sync-upstream.sh --dry-run` |
| 编译验证 | `go build`、`go vet`、`go test`、`tsc --noEmit` | CI pipeline |
| 冲突文件分类 | 按路径/关键字分类（Go/TS/配置/文档） | agent 读取 diff stat |
| 低风险冲突自动合并 | 仅 `my-docs/`、`README`、注释等纯本地文件 | 脚本判断 |
| 合并报告生成 | 输出变更摘要、冲突列表、风险评级 | agent 汇总 |

### 5.2 不能自动化的部分（必须由人决策）

- **语义冲突判断**：同名函数行为是否兼容
- **API 契约变更**：是否需要调整本地调用方
- **配置字段语义变化**：默认值变化是否影响本地运行
- **前端状态结构变化**：是否需要同步修改本地组件
- **是否回滚**：当合并后回归测试失败时

### 5.3 推荐自动化架构

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  触发器          │────▶│  预检 Agent      │────▶│  合并执行脚本    │
│ (cron/手动/GHA)  │     │ (dry-run + 分类) │     │ (git merge)     │
└─────────────────┘     └─────────────────┘     └─────────────────┘
                                                        │
                                ┌───────────────────────┼───────────────────────┐
                                ▼                       ▼                       ▼
                        ┌───────────────┐      ┌───────────────┐      ┌───────────────┐
                        │ 无冲突 / 低风险 │      │ 文本冲突        │      │ 语义冲突        │
                        │ 自动编译验证    │      │ agent 辅助解决  │      │ 人工介入        │
                        └───────────────┘      └───────────────┘      └───────────────┘
```

### 5.4 落地脚本示例

#### `scripts/sync-upstream.sh`

```bash
#!/bin/bash
set -euo pipefail

UPSTREAM_BRANCH="upstream/main-v2"
LOCAL_BRANCH="wkj-cli"
DRY_RUN=0

while [[ $# -gt 0 ]]; do
  case "$1" in
    --dry-run) DRY_RUN=1; shift ;;
    *) echo "Usage: $0 [--dry-run]"; exit 1 ;;
  esac
done

echo "=== 1. fetch upstream ==="
git fetch upstream

echo "=== 2. merge base ==="
BASE=$(git merge-base "$LOCAL_BRANCH" "$UPSTREAM_BRANCH")
echo "base: $BASE"

echo "=== 3. upstream commits since base ==="
git log --oneline "$BASE..$UPSTREAM_BRANCH"

echo "=== 4. changed files ==="
git diff --stat "$BASE" "$UPSTREAM_BRANCH"

echo "=== 5. conflict preview ==="
CONFLICTS=$(git merge-tree "$BASE" "$LOCAL_BRANCH" "$UPSTREAM_BRANCH" | grep -E '<<<<<<|======|>>>>>>' || true)
if [[ -n "$CONFLICTS" ]]; then
  echo "⚠️  detected conflicts:"
  echo "$CONFLICTS"
else
  echo "✅ no text conflicts detected"
fi

if [[ "$DRY_RUN" -eq 1 ]]; then
  echo "=== dry-run mode, stopping before merge ==="
  exit 0
fi

echo "=== 6. creating sync branch ==="
SYNC_BRANCH="sync/upstream-$(date +%Y%m%d-%H%M%S)"
git checkout -b "$SYNC_BRANCH" "$LOCAL_BRANCH"

echo "=== 7. merging ==="
if git merge "$UPSTREAM_BRANCH" -m "merge: sync upstream/main-v2"; then
  echo "✅ merge succeeded"
else
  echo "❌ merge failed, please resolve conflicts on $SYNC_BRANCH"
  exit 1
fi

echo "=== 8. validation ==="
if ! go build ./...; then
  echo "❌ go build failed"
  exit 1
fi

if ! go vet ./...; then
  echo "❌ go vet failed"
  exit 1
fi

echo "✅ sync branch ready: $SYNC_BRANCH"
```

#### `.github/workflows/upstream-sync-notify.yml`（可选）

```yaml
name: Upstream Sync Check
on:
  schedule:
    - cron: '0 9 * * 1'  # 每周一上午 9 点
  workflow_dispatch:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Fetch upstream
        run: |
          git remote add upstream https://github.com/esengine/DeepSeek-Reasonix.git
          git fetch upstream
      - name: Detect changes
        run: |
          BASE=$(git merge-base HEAD upstream/main-v2)
          COUNT=$(git rev-list --count "$BASE..upstream/main-v2")
          echo "upstream_commits=$COUNT" >> "$GITHUB_OUTPUT"
      - name: Notify
        if: steps.detect.outputs.upstream_commits > 0
        run: |
          echo " upstream/main-v2 有 ${{ steps.detect.outputs.upstream_commits }} 个新 commit，请执行 scripts/sync-upstream.sh --dry-run 预览冲突"
```

## 六、Agent 辅助合并的工作流

### 6.1 人工发起合并时

```text
用户：同步一下上游

agent 执行：
1. 运行 scripts/sync-upstream.sh --dry-run
2. 输出变更摘要 + 冲突风险评级
3. 询问用户：直接合并 / 创建隔离分支 / 先 review 再合并
4. 根据选择执行合并
5. 自动运行验证清单
6. 生成合并报告（含冲突文件、决策点、测试状态）
```

### 6.2 自动通知时

```text
cron / GHA 检测到上游更新：
1. 创建 issue 或发送通知
2. 附带 dry-run 结果
3. agent 标注风险文件（基于本地改动清单）
4. 等待人工确认后再执行真实合并
```

### 6.3 agent 解决文本冲突的原则

agent 可以尝试解决以下类型的文本冲突：

- 导入块冲突：双方都在同一文件新增 import
- 配置项冲突：双方新增不同字段
- 同文件不同函数：双方在不相邻位置新增代码

agent **不得**自动解决：

- 同一函数体内部的逻辑冲突
- 接口签名变更相关的冲突
- 涉及本地二开核心功能的冲突
- 无测试覆盖的文件的冲突

## 七、回滚预案

### 7.1 合并后发现问题

```bash
# 方式 1：reset 到合并前（如果未 push）
git reset --hard HEAD~1

# 方式 2：revert 合并提交（如果已 push）
git revert -m 1 <merge-commit-hash>

# 方式 3：用隔离分支重新合并
git checkout wkj-cli
git reset --hard <merge-commit-hash>^
git checkout -b sync/redo
git merge upstream/main-v2
# 重新解决冲突
```

### 7.2 最小可运行基线

每次成功合并后，立即打标签：

```bash
git tag sync-base-$(date +%Y%m%d) wkj-cli
git push origin sync-base-$(date +%Y%m%d)
```

这样回滚时可以直接回到上一个已知可运行的基线。

## 八、检查清单模板

### 8.1 合并前

- [ ] 当前分支无未提交改动
- [ ] 已 fetch 上游最新代码
- [ ] 已查看 `git log --oneline HEAD..upstream/main-v2`
- [ ] 已确认本地改动清单中的高风险文件
- [ ] dry-run 已执行且结果已 review

### 8.2 合并中

- [ ] 在隔离分支上执行合并
- [ ] 所有 `<<<<<<<` 已解决
- [ ] 本地二开核心功能文件已人工 review
- [ ] 分阶段提交，提交信息说明冲突解决策略

### 8.3 合并后

- [ ] `go build ./...` 通过
- [ ] `go vet ./...` 通过
- [ ] 关键包测试通过
- [ ] 前端类型检查通过
- [ ] 桌面端可构建
- [ ] 自定义功能手动回归通过
- [ ] 已打 `sync-base-YYYYMMDD` 标签

## 九、FAQ

### Q1：多久同步一次上游？

**建议每周一次。** 如果上游有破坏性变更，可以缩短到 2-3 天一次。超过两周不同步，单次合并风险会指数级上升。

### Q2：本地二开分支可以直接 push 到 origin 吗？

可以，但建议 push 到一个独立的 remote branch（如 `origin/wkj-cli`），不要与 `origin/main-v2` 混淆。

### Q3：agent 能完全替代人工合并吗？

**不能。** agent 可以处理预检、分类、编译验证和低风险文本冲突，但语义冲突、架构适配和回滚决策必须由人做。

### Q4：`my-docs/` 会和上游冲突吗？

通常不会，因为 `my-docs/` 是本地二开目录，上游不存在。即使上游未来新增同名目录，也可以通过 `.gitattributes` 或目录重命名隔离。

### Q5：遇到上游重构了本地改动的核心文件怎么办？

1. 暂停合并
2. 理解上游重构意图
3. 在隔离分支上重新实现本地功能，适配新结构
4. 不要强行保留旧代码结构
