## 设计原则

Hope 是**完全独立**的指令。与 goal 的关系仅限于：

- **第一阶段**：利用 goal 的成熟实现作为「行为对照模板」，完整复制其机械结构
- **复制完成后**：goal 与 hope 互不影响，各自独立演进

**禁止做法**：别名/映射/共享状态。`hope ≈ aliasOf(goal)` 不可接受。

---

## 概述

### 目标

创建 `/hope` 指令，**第一阶段与 `/goal` 行为完全一致**（状态机、循环、标记协议、Compse 注入、UI、持久化全等），但以**完全独立的代码副本**实现，为后续分化打下基础。

### 方法

对代码库中每一个包含 `goal` / `Goal` / `"goal"` 的源文件逐行追踪，回答三个问题：

1. **哪些代码必须平行复制**（带 `goal` 标识的独立逻辑、状态字段、UI 文案）
2. **哪些代码可以共享**（工具函数、通用引擎——但注意本轮不共享状态）
3. **最小改动路径是什么**

## 一、Goal 全链路的完整解剖

### 1.1 概念分层：引擎层 vs 标识层

```
引擎层（逻辑可复用，但本轮全部独立复制）
  ├─ for { advance(); runTurn(); }          ← 循环骨架
  ├─ 解析 [xxx:continue/complete/blocked]   ← 标记协议
  ├─ 相同原因 blocked 3 次停止               ← 保护机制
  └─ maxAutoTurns = 50 上限                  ← 保护机制

标识层（必须完全独立）
  ├─ 状态字段（c.goal vs c.hope）
  ├─ 命令名（/goal vs /hope）
  ├─ 标记前缀（[goal:xxx] vs [hope:xxx]）
  ├─ 提示词文本（"Goal mode: ..." vs "Hope mode: ..."）
  └─ UI 文案 + CSS 类名
```

引擎层**逻辑相同**、**数据不同**。代码层面不可共享——Go 是静态类型，`c.goal` 和 `c.hope` 是不同的 struct 字段，循环函数必须各自引用各自的字段。

### 1.2 完整调用链：从 `/hope 重构 boot 包` 到执行完毕

以下为 goal 的实际调用链（基于 v1.7.0 代码）。hope 必须在每一环平行复制：

```
用户输入 "/hope 重构 boot 包"
  │
  ▼ [dispatch 层] controller.go:778
  c.applyHopeCommand(trimmed, display)           ← 新增
  │
  ▼ [命令解析] input.go
  ParseHopeCommand(trimmed)                      ← 新增
  ├─ 返回 HopeCommand{Action: HopeCommandSet, Text: "重构 boot 包"}
  └─ 不匹配则 return false
  │
  ▼ [命令执行] controller.go (新增 applyHopeCommand)
  ├─ SetPlanMode(false)          // 退出 plan 模式
  ├─ SetHope("重构 boot 包")      // 设置 hope 状态字段
  │   └─ 内部自动 ClearGoal()    // 互斥
  └─ runGoalLoopWithRawDisplay(ctx, "Start pursuing...", "重构 boot 包", display)
      │  ┌──── 引擎函数名保留 runGoalLoopWithRawDisplay ────┐
      │  │  这是纯粹的引擎函数，不区分 goal/hope，内部调    │
      │  │  用 continueGoal / continueHope 由 Compose 的    │
      │  │  注入结果决定                                    │
      │  └─────────────────────────────────────────────────┘
      │
      ▼
  ┌─ Turn 1 ────────────────────────────────────┐
  │  Compose(input)                              │
  │    ├─ if goal active → activeGoalBlock()     │  ← 不动
  │    └─ if hope active → activeHopeBlock()     │  ← 新增分支
  │  Agent.Run(composed)                         │
  │  model → [hope:continue]                     │
  └──────────────────────────────────────────────┘
      │
      ▼ runGoalLoopWithRawDisplay → continueHope()
      │
  ┌─ Turn 2 ────────────────────────────────────┐
  │  Compose(hopeContinueTurn)                   │
  │    └─ if hope active → activeHopeBlock()     │
  │  Agent.Run(composed)                         │
  │  model → [hope:complete]                     │
  └──────────────────────────────────────────────┘
      │
      ▼ advanceHopeAfterTurn() → status=complete → return false
      │
      ▼ Hope 结束
```

**关键认识**：引擎函数 `runGoalLoopWithRawDisplay` / `runTurnWithRawDisplay` **保持不变**。它们只关心「当前是否有激活的目标循环」，不关心目标是 goal 还是 hope。行为分叉发生在 `Compose()`（注入不同提示词）和 `continueHope()` / `advanceHopeAfterTurn()`（读写不同状态字段）。

## 五、关键架构决策

### 决策 1：引擎复制策略

| 方案 | 优点 | 缺点 |
|------|------|------|
| **平行复制**（推荐） | 代码独立清晰，改动不影响 goal；后续分化成本低 | ~60 行重复代码；未来 bug fix 需两处同步 |
| **参数化** | 零重复，一次修复全生效 | 引入间接层，后续分化需拆参数 |

**建议**: 第一阶段平行复制。60 行重复在 ~571 行总改动中占比不大。后续稳定后可重构为参数化共享引擎。

### 决策 2：Goal/Hope 互斥

`SetHope()` 自动 `ClearGoal()`，反之亦然。共享同一个「运行中」状态槽。

### 决策 3：标记格式

Goal: `[goal:continue]` / `[goal:complete]` / `[goal:blocked:...]`
Hope: `[hope:continue]` / `[hope:complete]` / `[hope:blocked:...]`

`parseHopeStatusMarker()` 独立实现（搜索 `[hope:` 前缀）。

### 决策 4：前端 UI 复用

扩展 `CollaborationMode` 为四值 (`"normal" | "plan" | "goal" | "hope"`)，UI 渲染层统一按 mode 分支。

## 七、风险与缓解

| 风险 | 严重度 | 描述 | 缓解措施 |
|------|:------:|------|----------|
| **`continueGoal()` hidden side-effect** | 🔴 | `advanceGoalAfterTurn()` 不仅返回 bool，还修改 Controller 状态（`c.goal=""` on complete、`c.goalStatus=GoalStatusBlocked` on blocked）。`continueHope()` 必须精确复制 | 以 goal 代码为模板逐行对照，用 diff 验证 |
| **前端 `goalModeOn` 散落** | 🔴 | `goalModeOn` 在 Composer.tsx 约 15 处散布（输入验证、chip、placeholder、submit），直接复制会导致代码膨胀 | 引入 `intentModeOn = goalModeOn \|\| hopeModeOn` 聚合变量，大部分位置只查 `intentModeOn` |
| **Desktop Tab 持久化兼容** | 🟡 | 新增 `Hope/HopeStatus` JSON 字段后，旧版 Desktop 打开新会话 | Go `json:"hope,omitempty"` 保证安全；新版打开旧会话 `hope=""` 等价于无激活 hope |
| **goal bug 遗漏同步** | 🟡 | 修 goal 引擎时忘记同修 hope 的对应副本 | 在 goal 相关 PR/commit 模板中加 hope 检查项 |
| **测试覆盖缺口** | 🟡 | goal 已有 `goal_test.go`，hope 暂无 | 阶段 2 就写 `hope_test.go`，覆盖 SetHope/clear/completed/blocked 路径 |

## 九、结论

| 维度 | 结论 |
|------|------|
| 技术可行性 | ✅ **完全可行** |
