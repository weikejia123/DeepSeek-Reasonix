## 核心结论

**是的，Desktop 会话窗口有完善的三层滑动窗口机制，记录过多时不会显著影响性能。**

## 前端三层架构（Transcript.tsx）

Desktop 使用 **Hot/Warm/Cold 三层分区渲染策略** 来处理大量会话记录：

```
items[0]  ─┐
...        │ Cold Zone  ───  分页加载，点击"加载更多"才显示
           ├────────────  warmTurnStart
...        │ Warm Zone  ───  折叠为摘要卡片，点击展开
           ├────────────  hotStartIdx
items[N]  ─┤ Hot Zone   ───  完全渲染，实时更新
...        │
items[end] ┘
```

### 各层详细说明

| 层级 | 范围 | 渲染策略 | 性能影响 |
|------|------|----------|----------|
| **Hot Zone** | 最近 30 个用户回合 (`HOT_TURNS = 30`) | 完全渲染，实时更新 | 正常性能消耗 |
| **Warm Zone** | 30 回合之前的记录 | 折叠为摘要卡片，点击展开 | 极小，只渲染摘要 |
| **Cold Zone** | 更早的记录 | 分页加载，每页 20 条 (`WARM_PAGE_SIZE = 20`) | 零，不渲染 |

### 关键代码位置

- **分层计算**: `Transcript.tsx:257-270`
- **Hot Zone 渲染**: `Transcript.tsx:330-450`
- **Warm Zone 渲染**: `Transcript.tsx:450-600`
- **Cold Zone 分页**: `Transcript.tsx:600-650`

## 后端上下文压缩（compact.go）

前端的分层只是**视觉优化**，真正的性能保障来自后端的**上下文压缩机制**：

### 压缩触发阈值

```go
const (
    defaultSoftCompactRatio   = 0.5   // 50% 时报告上下文增长
    defaultCompactRatio       = 0.8   // 80% 时触发压缩
    defaultCompactForceRatio  = 0.9   // 90% 时强制压缩
    defaultCompactTarget      = 0.5   // 压缩后保留 50% 窗口
    defaultTailTokens         = 16384 // 保留的最近 tail 预算（token）
)
```

### 压缩流程

1. **监测**: 每回合检查 `PromptTokens / ContextWindow` 比例
2. **软通知**: 达到 50% 时报告但不压缩（保持缓存命中）
3. **触发压缩**: 达到 80% 时启动压缩
4. **强制压缩**: 达到 90% 时无论如何都压缩
5. **智能摘要**: 使用 LLM 将旧消息总结为结构化简报

### 压缩保留策略

- **用户消息**: 始终保留原文（不压缩）
- **最近 Tail**: 保留最近 16384 tokens 的完整记录
- **旧消息**: 压缩为摘要，包含：
  - 目标（Goal）
  - 决策与理由（Decisions & rationale）
  - 文件与代码（Files & code）
  - 命令与结果（Commands & outcomes）
  - 错误与修复（Errors & fixes）
  - 待办与下一步（Pending & next step）

## 性能影响分析

### 场景 1: 1000 条历史记录

| 组件 | 处理方式 | 性能影响 |
|------|----------|----------|
| 前端渲染 | 只渲染最近 30 回合 + 摘要卡片 | 流畅 |
| 后端存储 | 全量存储在内存 | 内存占用适中 |
| 后端压缩 | 旧记录已压缩为摘要 | API 调用高效 |

### 场景 2: 单条超大消息（如粘贴大文件）

| 组件 | 处理方式 | 性能影响 |
|------|----------|----------|
| 前端渲染 | 正常渲染（虚拟滚动不针对单条） | 可能卡顿 |
| 后端压缩 | 大文件内容会被摘要化 | 正常 |

### 场景 3: 长时间会话（100+ 回合）

| 组件 | 处理方式 | 性能影响 |
|------|----------|----------|
| 前端渲染 | Warm/Cold 分区，只显示摘要 | 流畅 |
| 后端压缩 | 定期压缩，保持上下文在窗口内 | 正常 |

## 可能的性能瓶颈

### 1. 超大单条消息

**问题**: 前端没有针对单条超大消息做虚拟滚动，如果一条消息包含 10MB 文本，渲染会卡顿。

**代码位置**: `Message.tsx` 没有 `react-window` 或类似虚拟化。

### 2. 频繁的压缩操作

**问题**: 如果配置的小窗口（如 4K tokens），会频繁触发压缩。

**解决**: 使用大窗口模型（如 128K/200K）。

### 3. 压缩时的 LLM 调用

**问题**: 压缩本身需要调用 LLM 生成摘要，有延迟。

**优化**: 压缩是异步的，不会阻塞用户交互。

## 配置建议

### 优化性能的配置

```toml
[agent]
# 使用大窗口模型，减少压缩频率
# 配合 DeepSeek-V4 的 100万 token 窗口
context_window = 1000000

# 调整压缩阈值（可选）
soft_compact_ratio = 0.5   # 50% 时报告
compact_ratio = 0.8        # 80% 时压缩
compact_force_ratio = 0.9  # 90% 时强制压缩
```

### 减少"过度思考"的配置

```toml
[agent]
# 禁用项目检查，减少回合数
disable_project_checks = true
```

## 总结

| 问题 | 答案 |
|------|------|
| 记录过多是否影响性能？ | **不会显著影响**，有三层滑动窗口保护 |
| 是否有滑动窗口能力？ | **有**，Hot/Warm/Cold 三层分区 |
| 后端是否有压缩？ | **有**，基于 token 比例的智能压缩 |
| 什么情况下会卡顿？ | 单条超大消息（>1MB 文本） |
| 如何优化？ | 使用大窗口模型 + 禁用不必要的检查 |

**结论**: Desktop 的会话窗口性能设计是完善的，正常使用时不会因为历史记录过多而卡顿。
